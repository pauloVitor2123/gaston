Ótimo, agora temos um leque bem claro:

- **Cache (Redis)** para estado de lançamentos pendentes. [getnerdify](https://getnerdify.com/blog/redis-cache-object/)
- **Banco (sem definir ainda)** para salvar os dados finais.  
- **Observação** como texto que pode ser chunkado e usado para busca semântica. [neura](https://www.neura.market/directories/claude/blog/mastering-claude-haiku-embeddings-semantic-search-in-node-js-apps)
- **Categorias** para: contas fixas, variáveis, boletos com vencimento, compras parceladas, cartões específicos (Nubank PJ, Nubank PF, Flash, Caixa, etc.).

Vou desenhar o MVP conceitual e os prompts para LLM 1 e LLM 2.

## 1. Arquitetura do MVP

### Blocos principais

1. **Telegram Bot (webhook)**  
   - Recebe mensagens do usuário.  
   - Encaminha para rota `POST /telegram/webhook` no Express. [core.telegram](https://core.telegram.org/bots/api)

2. **Express (Node.js)**  
   - Rota `/telegram/webhook`:  
     - Recebe o JSON do Telegram.  
     - Extrai: `chat_id`, `message_id`, `text`.  
     - Decide se é:
       - Comando explícito (`/add`, `/saldo`, etc.) → vai direto para serviço correspondente.  
       - Texto livre → vai para fluxo com LLM 1 → LLM 2.  
   - Serviços:
     - `criarLancamentoConversado`:  
       - Recebe texto do usuário.  
       - Chama LLM 1.  
       - Valida campos obrigatórios (valor, data, categoria, descrição).  
       - Se faltando algo → pergunta ao usuário.  
       - Se ok → chama LLM 2.  
       - Se LLM 2 responde com pergunta → pergunta ao usuário e repete quanto necessário (até 3).  
       - Quando tudo ok → salva no banco.  
   - Integra com:
     - Redis para cache do estado de lançamentos pendentes. [nodewire](https://nodewire.net/node-redis-caching/)
     - Banco (ex.: PostgreSQL, SQLite, etc.) para dados finais.

3. **Redis**  
   - Estrutura: chave `lancamento:{chat_id}:{message_id}`.  
   - Campos:
     - `json_intermediario` (JSON do LLM 1 ou do último ciclo).  
     - `perguntas_feitas` (array de strings).  
     - `quantidade_perguntas` (0–3).  
     - `iniciado_em` (timestamp).  
   - TTL por segurança (ex.: 24h) para não acumular dados antigos.

4. **LLM 1** (texto/conversa)  
   - Função: extrair campos básicos e identificação de cartões/contas.  
   - Retorna JSON com:
     - `valor`, `data`, `categoria`, `descricao`, `forma_pagamento`,  
     - `detalhes_pagamento` (ex.: `cartao_nubank_pf`, `cartao_caixa`, etc.),  
     - `tipo_lancamento`: `"simples"`, `"parcelado"`, `"boleto"`,  
     - `parcelas_total`, `primeira_data_parcela`,  
     - `data_vencimento` (para boletos),  
     - `missing_fields`: array de nomes de campos faltantes,  
     - `observacao`: string para texto livre contextual.

5. **LLM 2** (validação + categorias)  
   - Função:
     - Ajustar `categoria` conforme padrão.  
     - Sugerir nova categoria se necessário.  
     - Validar coerência geral (ex.: se `tipo_lancamento` é “parcelado”, tem `parcelas_total` e `primeira_data_parcela`).  
     - Se algo importante está ruim, pode fazer **uma pergunta consolidada** (que toca vários pontos em uma mensagem).  
   - Retorna:
     - `status`: `"ok"` ou `"precisa_input"`.  
     - `pergunta`: string (se `precisa_input`) ou `null`.  
     - `json_final`: JSON completo e validado.

6. **Banco de dados**  
   - Tabela `lancamentos`:
     - `id`, `chat_id`, `valor`, `categoria`, `descricao`, `data`,  
     - `forma_pagamento`, `detalhes_pagamento`,  
     - `tipo_lancamento`, `parcelas_total`, `primeira_data_parcela`,  
     - `data_vencimento`,  
     - `observacao` (texto).  
   - Tabela `integracoes_cardapio` (opcional, para mapear categorias fixas/variáveis).  
   - Mais tabelas para dashboards (ex.: `categorias`, `contas_fixas`, etc.) podem ser adicionadas depois.

## 2. Exemplo de fluxo concreto

### Passo 1 – Usuário manda mensagem

Usuário escreve:

> “paguei 150 de luz ontem no cartão nubank pf, é uma conta fixa”

### Passo 2 – Express recebe e chama LLM 1

Express extrai:

- `chat_id`, `text` = “paguei 150 de luz ontem no cartão nubank pf, é uma conta fixa”.

Express chama LLM 1 com prompt (veja abaixo).

### Passo 3 – LLM 1 responde

LLM 1 retorna:

```json
{
  "valor": 150,
  "categoria": "luz",
  "data": "2026-07-13",
  "descricao": "luz",
  "forma_pagamento": "cartão",
  "detalhes_pagamento": "cartao_nubank_pf",
  "tipo_lancamento": "simples",
  "missing_fields": [],
  "observacao": "conta fixa"
}
```

### Passo 4 – Node valida campos obrigatórios

Node verifica: valor, data, categoria, descrição estão presentes?  
Sim → chama LLM 2.

### Passo 5 – LLM 2 ajusta

LLM 2 analisa e:

- Muda `categoria` de `"luz"` para `"energia"`.  
- Mantém todo o resto.  
- Não precisa de perguntas.

Retorna:

```json
{
  "status": "ok",
  "pergunta": null,
  "json_final": {
    "valor": 150,
    "categoria": "energia",
    "data": "2026-07-13",
    "descricao": "luz",
    "forma_pagamento": "cartão",
    "detalhes_pagamento": "cartao_nubank_pf",
    "tipo_lancamento": "simples",
    "observacao": "conta fixa"
  }
}
```

### Passo 6 – Node salva no banco

Node committing o `json_final` na tabela `lancamentos`.

## 3. Prompts para LLM 1 e LLM 2

### Prompt LLM 1 – Extração de dados

Usa modelo rápido (ex.: `claude-haiku`, `gpt-4o-mini`, etc.).

```text
Você é um assistente especializado em extrair informações de despesas de mensagens em português.

O usuário vai enviar uma mensagem descrevendo um gasto (ex: "paguei 150 de luz ontem no cartão nubank pf").

Você deve:
1) Extrair os campos abaixo e devolvá-los em um JSON:
   - valor: número (float)
   - data: ISO 8601 (YYYY-MM-DD), inferindo "ontem", "hoje", "semana passada", etc.
   - categoria: nome da categoria (ex: "luz", "mercado", "transporte", "aluguel", etc.)
   - descricao: texto curto que descreva o gasto
   - forma_pagamento: "cartão", "débito", "dinheiro", "débito automático", etc.
   - detalhes_pagamento: se foi cartão, indicar qual exatamente entre:
     - "cartao_nubank_pf"
     - "cartao_nubank_pj"
     - "cartao_flash"
     - "cartao_caixa"
     - "cartao_outro"
     Se não cartão, pode ser null.
   - tipo_lancamento: "simples", "parcelado", "boleto"
   - parcelas_total: número (só se tipo_lancamento == "parcelado")
   - primeira_data_parcela: ISO 8601 (só se tipo_lancamento == "parcelado")
   - data_vencimento: ISO 8601 (só se tipo_lancamento == "boleto")
   - missing_fields: array de strings com nomes dos campos que estão faltantes ou muito ambíguos
   - observacao: string livre com contexto relevante que o usuário mencionou (ex: "conta fixa", "primeira parcela", etc.)

2) Se o usuário não mencionou algo claramente, não invente: coloque `null` ou inclua em `missing_fields`.

3) Responda apenas com o JSON, sem explicações.

Exemplo de saída:
{
  "valor": 150,
  "data": "2026-07-13",
  "categoria": "luz",
  "descricao": "luz",
  "forma_pagamento": "cartão",
  "detalhes_pagamento": "cartao_nubank_pf",
  "tipo_lancamento": "simples",
  "parcelas_total": null,
  "primeira_data_parcela": null,
  "data_vencimento": null,
  "missing_fields": [],
  "observacao": "conta fixa"
}
```

### Prompt LLM 2 – Validação e ajuste de categoria

Usa modelo mais preciso (ex.: Claude 3.5, GPT-4, etc.).

```text
Você é um validador e organizador de estrutura de despesas.

Você receberá um JSON já extraído de uma mensagem do usuário, com os seguintes campos:
- valor
- data
- categoria (nome em português)
- descricao
- forma_pagamento
- detalhes_pagamento
- tipo_lancamento: "simples", "parcelado", "boleto"
- parcelas_total
- primeira_data_parcela
- data_vencimento
- observacao

Você deve:
1) Analisar a coerência interna do JSON:
   - Se tipo_lancamento == "parcelado", parcelas_total e primeira_data_parcela devem estar presentes e não null.
   - Se tipo_lancamento == "boleto", data_vencimento deve estar presente e não null.
   - Se algum desses campos obrigatórios por tipo está faltando, indicar em `pergunta`.

2) Ajustar a categoria:
   - Se a categoria parece ambígua ou muito genérica, sugira uma categoria mais adequada e padrão.
   - Exemplos:
     - "luz" → "energia"
     - "mercado" → "mercado" (ok)
     - "aluguel" → "aluguel" (ok)
   - Se a categoria é muito genérica, mas a observação ajuda a diferenciá-la (ex: "conta fixa"), use isso para escolher uma categoria mais específica.

3) Se precisar de mais informações para validar ou ajustar algo, faça UMA pergunta consolidada (não várias perguntas separadas).
   - Considere já todas as perguntas que já foram feitas antes (se houverem).
   - Não repetir perguntas.
   - A pergunta deve ser curta e clara, em português.

4) Responda com um JSON no formato:
{
  "status": "ok" ou "precisa_input",
  "pergunta": "texto da pergunta" ou null,
  "json_final": {
    "valor": ...,
    "data": ...,
    "categoria": ...,
    "descricao": ...,
    "forma_pagamento": ...,
    "detalhes_pagamento": ...,
    "tipo_lancamento": ...,
    "parcelas_total": ...,
    "primeira_data_parcela": ...,
    "data_vencimento": ...,
    "observacao": ...
  }
}

Se `status` == "ok", então `pergunta` deve ser null e `json_final` deve estar completo e coerente.
Se `status` == "precisa_input", então `pergunta` deve conter a pergunta consolidada e `json_final` pode ser parcial (com o que já está válido).
```
